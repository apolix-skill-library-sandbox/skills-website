Who does what

Every department has two GitHub teams in the {{ORG}} organization: one for everyone in the department, and a smaller leads team that approves changes.

Team member

Writes new skills and improves existing ones on a branch, then opens a pull request.

Department lead

Is asked to review automatically, gives feedback, approves and merges.

Management leads & admin

Own the review rules themselves (the .github/ folder) and the shared library.

The review flow

Nobody can change main directly. Every change goes through a pull request that a lead of that department approves.

Add a skill in the browser

No installs needed. Everything happens on github.com.

  1. Open your department's repository from the table above.
  2. Click Add file → Create new file.
  3. In the name field, type your-skill-name/SKILL.md. Typing the / creates the folder.
  4. Paste the template below and fill it in.
  5. Click Commit changes…, choose Create a new branch for this commit and start a pull request, and click Propose changes.
  6. Optional: add an icon. On your new branch, open the skill folder, click Add file → Upload files, upload icon.svg or icon.png, and commit to the same branch.
  7. Click Create pull request. Your department's leads are added as reviewers automatically.
  8. If the lead asks for changes, open the file on your branch, edit it with the pencil icon, and commit to the same branch. The pull request updates by itself.

To improve an existing skill, open its SKILL.md, click the pencil icon, and continue from step 5.

SKILL.md template

---
name: your-skill-name
description: What the skill does, and when Claude should use it. For example: "Use when the user asks to …".
---

# Your Skill Name

What Claude should do, step by step.

## Rules
- …

## Example
**User:** …
**Claude:** …

Try it before you submit. Zip your skill folder, upload it under Customize → Skills in Claude, and test it on a few real requests.

Add a skill with Claude Code

If you use Claude Code, you can ask it to do the whole thing, for example: "Create a skill called meeting-notes in the skills-sales repo of {{ORG}} and open a pull request." Or by hand:

gh repo clone {{ORG}}/skills-sales
cd skills-sales
git switch -c add-meeting-notes
mkdir meeting-notes        # then write meeting-notes/SKILL.md
git add meeting-notes
git commit -m "feat: add meeting-notes skill"
git push -u origin add-meeting-notes
gh pr create --fill

Writing a good skill

  • Folder name = skill name: lowercase letters, numbers and hyphens, like invoice-checker. The file is always SKILL.md.
  • The description does the work. Claude reads it to decide when to use the skill, and this site shows it on the card. Say what it does and when to use it.
  • Keep it short and concrete. Steps, rules and one or two examples beat long explanations.
  • Tell Claude what not to guess. If a skill depends on company facts like prices, policies or names, say where they come from, or have Claude ask.
  • These repositories are public. Never put client names, internal numbers, passwords or personal data in a skill.

For leads: reviewing

You're asked to review automatically whenever someone opens a pull request in your department's repository. Find everything waiting for you at github.com/pulls/review-requested.

  1. Open the pull request and go to Files changed.
  2. Click a line to comment on it, or suggest an exact rewrite with the ± suggestion button.
  3. Click Review changes and choose Approve or Request changes.
  4. Once approved and all conversations are resolved, click Merge pull request. Squash and merge keeps the history tidy.

What to check

  • Folder and file follow the naming convention, and name matches the folder.
  • The description clearly says what the skill does and when to use it.
  • The instructions are correct for how your department actually works.
  • Nothing confidential, since the repository is public.
  • It doesn't duplicate an existing skill. Improving the existing one is usually better.

Good to know

  • A pull request needs one approval from a lead of that department.
  • If new commits are pushed after you approved, your approval is removed and you review again.
  • The most recent push must be approved by someone other than the person who pushed it. So when a lead writes a skill, another lead approves it.
  • Changes to the review rules in .github/ need management leads or an admin.
